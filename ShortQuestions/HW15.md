### Q1
Virtual machines virtualize hardware and run a full guest operating system for each instance, resulting in higher resource overhead and slower startup times. Containers virtualize at the operating system level, sharing the host kernel while isolating applications using namespaces and cgroups. Because containers do not require booting a full OS, they are significantly more lightweight and start much faster.
### Q2
Linux namespaces and cgroups are the two core kernel features that enable containerization. Namespaces provide isolation by giving containers their own view of system resources, making each container appear as an independent environment. For example, the PID namespace isolates process IDs so that a container only sees its own processes, the NET namespace isolates networking resources such as IP addresses and ports, and the MNT namespace isolates filesystem mount points so containers only see their own file systems.

Cgroups provide resource control by limiting and accounting for how much CPU, memory, and I/O a container can use. While namespaces define what a container can see, cgroups define how many resources it can consume. Together, namespaces and cgroups allow containers to run in isolated environments with controlled resource usage while sharing the same Linux kernel, which makes containers lightweight and efficient.
### Q3
Container images are composed of multiple stacked read-only layers, where each layer represents a filesystem change such as installing packages or adding application code. These layers are immutable and can be shared across many containers. When a container is created from an image, the container runtime adds a thin writable layer on top of the image layers, which is used to store all runtime changes made by that container.

The copy-on-write (CoW) mechanism ensures that image layers are not duplicated unless a modification occurs. If a container needs to modify a file from a read-only layer, that file is first copied into the writable layer and then modified there, while unchanged files continue to be shared. This approach significantly reduces storage usage, improves performance, speeds up container startup, and allows many containers to efficiently run from the same image without interfering with each other.
### Q4
The Open Container Initiative (OCI) is an open governance body established to define industry-wide standards for container technologies, ensuring interoperability and portability across different container tools and platforms. The goal of OCI is to prevent vendor lock-in and allow containers built with one tool to run consistently using another, fostering a healthy and open container ecosystem.

OCI defines three main specifications. The Runtime Specification describes how a container should be run, including process execution, filesystem layout, and resource isolation, and is implemented by runtimes such as `runc`. The Image Specification defines how container images are built, structured, and stored as layered filesystems. The Distribution Specification standardizes how container images are pushed, pulled, and stored in registries. Together, these standards enable consistent container behavior, efficient image sharing, and seamless interoperability between tools like Docker, containerd, and Kubernetes.
### Q5
In the container runtime architecture, Kubernetes acts as the orchestration layer, responsible for managing containers at a cluster level. Kubernetes handles scheduling pods to nodes, managing desired state, scaling, service discovery, and failure recovery. It does not run containers directly; instead, it communicates with the node’s container runtime through the Container Runtime Interface (CRI).

The high-level runtime, such as containerd or CRI-O, runs on each Kubernetes node and is responsible for container lifecycle management. This includes pulling container images, managing storage and networking setup, and coordinating container creation and deletion. The high-level runtime translates Kubernetes’ CRI requests into concrete container operations and delegates low-level execution details to a lower-level runtime.

The low-level runtime, typically `runc`, implements the OCI Runtime Specification and directly interacts with the Linux kernel. It creates containers by configuring namespaces, cgroups, and filesystem mounts, and then starts the container process. Together, these layers form a clear hierarchy where Kubernetes orchestrates, high-level runtimes manage container lifecycles, and low-level runtimes interface with the Linux kernel to provide isolation and execution.
### Q6
The Container Runtime Interface (CRI) is a standardized API that allows Kubernetes to interact with different container runtimes in a consistent way. Instead of Kubernetes depending on a specific runtime implementation, CRI acts as an abstraction layer between the kubelet and the container runtime, enabling Kubernetes to support multiple runtimes such as containerd and CRI-O without changing its core logic.

CRI defines two main services: RuntimeService and ImageService. The RuntimeService is responsible for container lifecycle operations, including creating and starting containers, stopping and removing containers, managing pods (sandboxes), and retrieving container status. The ImageService handles image-related operations such as pulling images from registries, listing images, and removing unused images from the node.

By introducing this abstraction, CRI decouples Kubernetes from any single container runtime, improving flexibility, interoperability, and extensibility. This design allows runtime implementations to evolve independently while ensuring Kubernetes remains portable, vendor-neutral, and easier to maintain across different container environments.
### Q7
Before JDK 8u191 and JDK 10, the JVM was not container-aware. It detected available memory and CPU based on the host machine instead of container limits enforced by cgroups. As a result, when running inside containers, Java applications often allocated too much heap memory, ignored memory limits, and were frequently terminated by the OOM killer. This made Java unreliable and difficult to tune in containerized environments.

Modern JDK versions introduced container awareness by reading cgroup constraints to determine available memory and CPU resources. The JVM now automatically sizes the heap based on container limits rather than host resources. Instead of fixed heap sizes, JVMs support percentage-based memory configuration, allowing applications to scale correctly across different container sizes.

For production containers, recommended JVM options include `-XX:MaxRAMPercentage` (and optionally `-XX:InitialRAMPercentage`) to control heap size as a percentage of container memory, rather than using hardcoded `-Xmx` values. These improvements are critical in production because they prevent unexpected OOM kills, improve resource efficiency, and allow Java services to behave predictably in Kubernetes and other container orchestration platforms.
### Q8
Multi-stage Docker builds allow a Dockerfile to use multiple build stages, where each stage has its own base image and purpose. Typically, early stages are used for compiling or building an application with all required build tools, while the final stage contains only the minimal runtime environment and the build artifacts. By copying only the necessary outputs (such as binaries or JAR files) from the build stage into the final stage, multi-stage builds avoid including unnecessary tools and dependencies in the final image.

This approach is especially important for reducing image size, improving security, and speeding up deployment. For example, in a Java/Maven application, one stage can use a Maven image with JDK and build tools to compile the application, while the final stage uses a lightweight JRE image to run the generated JAR. This can reduce image size by hundreds of megabytes, minimize the attack surface, and result in faster image pulls, quicker container startup, and more efficient deployments in production environments such as Kubernetes.
### Q9
Docker provides several network modes to support different connectivity and isolation needs. Bridge mode is the default and connects containers to a virtual bridge on the host, allowing containers to communicate with each other while using port mapping to expose services externally; it is suitable for most single-host applications. Host mode removes network isolation and lets the container share the host’s network stack, offering better performance but less isolation, and is typically used for performance-sensitive applications. None mode disables networking entirely and is useful for highly isolated or batch jobs that do not require network access. Overlay mode enables containers running on different hosts to communicate over a virtual network, making it essential for multi-node deployments such as Docker Swarm or Kubernetes clusters.

In Kubernetes, CNI (Container Network Interface) plugins are responsible for implementing pod networking. Kubernetes itself defines the networking model, but CNI plugins such as Flannel, Calico, and Cilium handle IP address allocation, routing, and network policies. CNI plugins ensure that pods can communicate across nodes, enforce isolation and security policies, and provide a consistent networking abstraction independent of the underlying infrastructure.
### Q10
Containers support multiple storage types with different persistence and performance characteristics. Named volumes are managed by Docker and persist independently of container lifecycles, making them ideal for databases and long-lived application data. Bind mounts map a specific host directory into a container, offering high performance and direct access to host files, but at the cost of portability and increased coupling to the host filesystem. tmpfs mounts store data in memory only and are removed when the container stops, providing the fastest I/O but no persistence.

In practice, named volumes are preferred for production data due to their portability and lifecycle management, bind mounts are commonly used in development environments for live code editing and debugging, and tmpfs is used for sensitive or temporary data such as caches or secrets. Choosing the correct storage type is important for balancing performance, persistence, security, and operational flexibility in containerized applications.
