### Q1
#### Topic
A Topic in Kafka is a logical category or feed name to which records are published. It acts like a table in a database where messages are organized.
#### Partition
A Partition is a physical subdivision of a topic. Each topic is split into one or more partitions.

Partitions allow Kafka to:
* Scale horizontally
* Enable parallel processing
* Maintain message ordering within a partition

Each partition is an ordered, immutable sequence of records, where each record is assigned a unique offset.
#### Broker
A Broker is a Kafka server that stores data and serves client requests.

A Kafka cluster consists of multiple brokers. Each broker:
* Stores partitions of topics
* Handles read and write requests
* Participates in leader election

Each partition has one leader broker and zero or more follower brokers (replicas). Producers and consumers communicate only with the leader of a partition.
#### Consumer group
A Consumer Group is a group of consumers that work together to consume messages from a topic.

Key rules:

* Within a consumer group, each partition is consumed by only one consumer.

* Different consumer groups can independently consume the same topic.

Consumer groups enable:

* Parallel processing

* Load balancing

* Scalability

If a consumer fails, Kafka automatically rebalances partitions among the remaining consumers.
#### Producer
A Producer is a client application that publishes (writes) messages to Kafka topics.

The producer:

* Sends messages to a specific topic

* Determines which partition the message should go to

Partition selection can be based on:

* A key (using a hash function)

* Round-robin strategy (if no key is provided)

Producers can also configure acknowledgment settings to ensure reliability.
#### Offset
An Offset is a unique identifier assigned to each record within a partition.

Offsets:

* Represent the position of a message in a partition

* Are used by consumers to track their progress

Consumers periodically commit offsets so that they can resume processing from the correct position after a restart or failure.
#### Zookeeper
ZooKeeper is a distributed coordination service that was traditionally used by Kafka for cluster management.

It was responsible for:

* Broker registration

* Leader election

* Metadata management

* Detecting failures
### Q2
When N ≥ M:

Each consumer in the consumer group will be assigned at least one partition.
Some consumers may handle multiple partitions.
This enables parallel processing and efficient resource utilization.

When N < M:

Some consumers will remain idle because each partition can only be consumed by one consumer within the same consumer group.
The maximum parallelism is limited by the number of partitions.

### Q3
Brokers are the servers that store topic data.
Each topic is divided into partitions, and those partitions are distributed across multiple brokers in the cluster.

For each partition:

* One broker acts as the leader

* Other brokers act as followers (replicas)

Producers and consumers communicate only with the leader broker of a partition.
Followers replicate data from the leader to ensure fault tolerance.
### Q4
Kafka uses a pull model.

Consumers actively request (poll) messages from brokers.
The broker does not push messages to consumers.

This design:

* Allows consumers to control their processing speed

* Prevents overload

* Improves scalability
### Q5
Kafka provides at-least-once delivery by default, so duplicates may occur.

To avoid duplicates:

* Enable idempotent producers

* Use exactly-once semantics (EOS) with transactions

* Carefully manage offset commits (commit only after successful processing)

* Implement idempotent processing logic in consumers

Exactly-once guarantees require both Kafka configuration and application-level design.
### Q6
If some consumers fail:

* Kafka triggers a rebalance

* Partitions assigned to the failed consumers are reassigned to active consumers

No data loss occurs because:

* Messages are stored in brokers

* Offsets are committed separately

The only possible issue is temporary reprocessing of messages if offsets were not committed before failure.

### Q8
Consumer lag is the difference between:

* The latest offset in a partition

* The committed offset of a consumer

* Lag indicates that consumers are behind producers.
Causes:

* Slow processing

* Insufficient consumers

* Heavy workload

Solutions:

* Increase number of partitions

* Add more consumers

* Optimize processing logic

* Scale brokers

* Increase hardware resources
### Q9
