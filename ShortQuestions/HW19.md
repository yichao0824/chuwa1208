### Q1 When should you use multi-threading versus async/non-blocking I/O? Give specific examples of scenarios for each approach.
Multi-threading is most appropriate when the workload is CPU-bound, meaning the program spends most of its time performing computations rather than waiting. Examples include image processing, encryption, sorting large datasets, machine learning inference, or complex business logic. In these cases, multiple threads can run in parallel on multiple CPU cores, improving performance by utilizing hardware concurrency. However, too many threads may introduce overhead due to context switching, so a fixed-size thread pool is usually recommended.
```java
import java.util.concurrent.*;

public class CpuThreadDemo {
    static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newFixedThreadPool(4);
        
        Future<Long>future = pool.submit(() -> {
            long sum = 0;
            for (int i = 0; i < 1_000_000; i+=) {
                sum += i;
            }
            return sum;
        });
        System.out.println("Result: " + future.get());
        pool.shutdown();
    }
}
```

Async/non-blocking I/O is better suited for I/O-bound workloads, where the application spends most of its time waiting for external resources such as databases, file systems, or remote services. Instead of blocking a thread during waiting, async programming allows the system to handle other tasks while the I/O operation is in progress. This is especially useful in high-concurrency systems such as web servers, API gateways, and microservices architectures.
```java
import java.net.URI;
import java.net.http.*;
import java.util.concurrent.CompletableFuture;

public class AsyncDemo {
    public static void main(String[] args) {
        HttpClient client = HttpClient.newHttpClient();
        
        HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create("https://example.com"))
                .GET()
                .build();
        CompletableFuture<Void> future =
                client.sendAsync(request, HttpResponse.BodyHandler.ofString())
                        .thenApply(HttpRequest::body)
                        .thenAccept(body -> System.out.println("Length: " + body.length()));
        future.join();
    }
}
```
### Q2 What are Virtual Threads in Java 21? Explain how they differ from platform threads and when you should (or should not) use them.
Virtual Threads are a lightweight implementation of threads introduced in Java 21 as part of Project Loom. Unlike traditional platform threads (also called OS threads), virtual threads are managed by the Java Virtual Machine (JVM) rather than being directly tied one-to-one with operating system threads. This allows Java applications to create thousands or even millions of threads with very low memory overhead.

Use Virtual Threads:
High I/O wait time (DB queries, HTTP calls)
Need simple blocking code style
Many concurrent connections

Avoid Virtual Threads:
CPU-Intensive computation
Using Synchronized blocks extensively
Relying on ThreadLocal for long durations

Virtual Threads = "cheap threads for blocking code"

### Q3 Compare Lock-based synchronization and CAS (Compare-And-Swap). When would you choose one over the other?
Lock-based synchronization (such as synchronized or ReentrantLock) works by allowing only one thread to enter a critical section at a time. Other threads must wait (block) until the lock is released. This guarantees mutual exclusion and is simple to reason about, but blocking may cause context switching overhead and reduce scalability under high contention.

CAS (Compare-And-Swap) is a non-blocking mechanism implemented at the CPU level. It works by atomically checking whether a variable has an expected value and, if so, updating it to a new value. If the value has changed, the operation fails and is typically retried in a loop. CAS avoids blocking and can achieve better performance in low-contention scenarios, but it may lead to repeated retries (spin) under high contention.
### Q4 What are the four necessary conditions for a deadlock to occur? Explain how "lock ordering" prevents deadlock.
A deadlock occurs when a group of threads are permanently blocked because each thread is waiting for a resource held by another thread. For a deadlock to happen, four necessary conditions (known as Coffman conditions) must all hold at the same time.

1. Mutual Exclusion
2. Hold and Wait
3. No preemption
4. Circular Wait

Example:

### Q6 What is exponential backoff with jitter? Why is jitter important when implementing retry logic?
Exponential backoff is a retry strategy where the delay between retry attempts increases exponentially after each failure. Instead of retrying immediately, the system waits longer and longer between attempts.

Jitter means adding randomness to the backoff delay. Instead of all clients waiting exactly 400 ms, each client waits for a slightly different random amount of time.
### Q7 Explain the three states of a Circuit Breaker (CLOSED, OPEN, HALF-OPEN) and how transitions between them work.
The Circuit Breaker pattern is used in distributed systems to prevent cascading failures when a dependent service becomes slow or unavailable. It works similarly to an electrical circuit breaker: when failures exceed a threshold, the system “opens” the circuit to stop further calls and allow recovery.

1. CLOSED State: In the CLOSED state, requests flow normally to the downstream service
2. In the OPEN state, requests are not sent to the downstream service.
3. In the HALF-OPEN state, the circuit breaker allows a small number of test requests to pass through.
### Q8 Why is "exactly-once delivery" considered impossible in distributed systems? How can you achieve "exactly- once processing" instead?
“Exactly-once delivery” is considered impossible in distributed systems because networks are unreliable and failures are ambiguous. If a sender does not receive an acknowledgment, it cannot know whether the message was lost or successfully processed but the acknowledgment was lost. To avoid data loss, the sender must retry, but retries can create duplicates. Because of this uncertainty, systems can only realistically guarantee at-most-once or at-least-once delivery, not true exactly-once delivery at the network level.

However, we can achieve exactly-once processing at the application level. The common approach is to allow duplicate delivery (at-least-once) but ensure that duplicates do not cause duplicate side effects. This is typically done using idempotent operations, unique message IDs for deduplication, and transactional updates. For example, storing a processed message ID in a database with a unique constraint ensures the same message cannot be applied twice.
### Q9 Compare the three caching patterns: Cache-Aside, Write-Through, and Write-Behind. What are the trade-offs of each?
Cache-Aside (a.k.a. lazy loading) means the application reads from the cache first, and on a cache miss it loads the data from the database and then puts it into the cache. Writes go directly to the database, and the app typically invalidates or updates the cache entry. The main benefit is simplicity and efficiency (only hot data gets cached), but the trade-off is that a miss causes extra latency and under high load you can get “cache stampedes” where many requests miss and hit the database at the same time. Consistency is also tricky because you must carefully invalidate/update cache after writes.

Write-Through means every write goes to the cache and the cache synchronously writes to the database (or the application writes to cache and DB in one step). Reads are fast because the cache is always up-to-date after a successful write, so consistency between cache and DB is easier. The trade-off is higher write latency (because the write waits on the database) and higher cost/traffic since even rarely-read data gets written into the cache.

Write-Behind (Write-Back) means the application writes to the cache first and the cache returns success immediately, then the cache flushes updates to the database asynchronously later (often in batches). This improves write throughput and reduces DB load, which is great for write-heavy workloads. The trade-off is weaker durability/consistency: if the cache crashes before the flush, data can be lost, and the database can be temporarily stale. It also increases complexity because you need retry, ordering guarantees, and failure handling for the async write pipeline.
### Q10 What is cache stampede (also known as cache breakdown)? Describe two solutions to prevent it.
A cache stampede (or cache breakdown) happens when a popular cache entry expires or is evicted, and many requests simultaneously try to fetch the same data from the database. Since the cache no longer has the value, all those requests hit the backend at once, potentially overwhelming the database and causing high latency or even system failure. This usually happens with hot keys that receive heavy traffic.

One common solution is locking (or request coalescing). When the cache entry expires, only one request is allowed to fetch the data from the database while others wait or return a temporary response. Once the first request reloads the cache, the waiting requests read from the cache instead of hitting the database. This prevents a sudden surge of identical backend queries.

Another solution is early expiration or randomized TTL (jitter). Instead of letting many hot keys expire at the exact same time, you add randomness to the expiration time or refresh the cache proactively before it expires. This spreads out cache rebuild operations and reduces the chance of many requests hitting the database simultaneously.
