### Q1 What are the three pillars of observability, and what is the primary purpose of each?
Observability is built on three main pillars: metrics, logs, and traces. Each pillar provides a different perspective on how a system behaves and helps engineers understand and debug complex systems.

Metrics are numerical measurements collected over time, such as CPU usage, request rate, latency, and error rate. Their primary purpose is to give a high-level view of system health and performance, making them ideal for monitoring, dashboards, and alerting when something goes wrong.

Logs are detailed, discrete records of events that happen within a system, often including error messages and contextual information. They are mainly used for troubleshooting and root-cause analysis by explaining what exactly happened inside the system.

Traces track a single request as it flows through multiple services in a distributed system, showing where time is spent and where failures occur. Their main purpose is to locate performance bottlenecks and understand service-to-service interactions.
### Q2 Explain the four common metric types and give an example use case for each.
There are four common metric types used in observability systems: counter, gauge, histogram, and summary. Each type is designed to model a different kind of behavior in a system.

A counter is a metric that only increases (or resets to zero on restart). It is used to track how many times something has happened. A common use case is counting the total number of HTTP requests received or the total number of errors that have occurred since the service started.
`http_requests_total = 125432`, `login_failures_total = 87`

A gauge represents a value that can go up or down over time. It is used to measure the current state of something. Typical examples include current memory usage, CPU utilization, number of active connections, or the size of a queue.
`memory_usage_bytes = 2.3GB`, `active_connections = 142`

A histogram samples observations and groups them into configurable buckets, allowing you to analyze distributions. It is often used for request latency or response size, where you want to know not just the average but how values are spread (for example, how many requests took less than 100 ms, 500 ms, or 1 second).
`<100ms : 8,000 requests`, `<300ms : 15,000 requests`, `<1s : 19,500 requests`

A summary is similar to a histogram but focuses on calculating quantiles (such as p50, p95, p99) over a sliding time window. It is commonly used for latency measurements when precise percentile values are important, such as tracking the 99th percentile response time for a critical API endpoint.
`latency_p50 = 120ms`, `latency_p95 = 450ms`, `latency_p99 = 980ms`
### Q3 What is structured logging, and why is it preferred over unstructured (plain text) logging in production systems?
Structured logging is a logging approach where log entries are recorded in a consistent, machine-readable format (commonly JSON) with clearly defined fields such as timestamp, log level, service name, request ID, and error code. Each log message is treated as structured data rather than free-form text.

It is preferred over unstructured (plain text) logging in production systems because structured logs are easy to parse, search, filter, and aggregate by log management systems. This makes it much more efficient to perform debugging, monitoring, and analytics at scale, especially in distributed or microservices environments.

In contrast, unstructured logs are designed mainly for human readability and are difficult to analyze automatically. As systems grow in size and complexity, structured logging enables faster root-cause analysis, better correlation with metrics and traces, and more reliable observability overall.
### Q4 Explain the relationship between Trace, Span, and Context Propagation in distributed tracing.
In distributed tracing, a trace represents the complete lifecycle of a single request as it travels through a distributed system, often crossing multiple services. A trace is composed of multiple spans, where each span represents a single unit of work, such as handling an HTTP request, calling a downstream service, or executing a database query. Spans contain timing information and parent–child relationships, allowing the system to reconstruct the full request path and understand where time is spent.

Context propagation is the mechanism that connects spans together into a single trace across service boundaries. When a service makes a downstream call, it propagates trace context (such as trace ID and parent span ID) via headers or metadata. This ensures that all spans created by different services are linked to the same trace, enabling end-to-end visibility, accurate latency analysis, and effective debugging in distributed systems.
### Q5 Prometheus uses a "pull" model for collecting metrics. Explain how this works and what are its advantages and disadvantages compared to a "push" model.
In the pull model used by Prometheus, each monitored service exposes its metrics through an HTTP endpoint (commonly /metrics). Prometheus periodically scrapes these endpoints at a fixed interval to collect metrics. This means the monitoring system actively requests data from targets rather than having targets send data on their own.

One major advantage of the pull model is simplicity and reliability. Prometheus always knows whether a target is reachable, making it easy to detect down services. It also allows centralized control over scrape intervals, labels, and service discovery, which works especially well in dynamic environments like containers and microservices. Additionally, targets do not need credentials or configuration for the monitoring server, reducing coupling.

However, the pull model also has disadvantages. It can be difficult to use for short-lived jobs or services behind firewalls that Prometheus cannot reach. In contrast, a push model (where services send metrics to a central collector) handles these cases more naturally. Push systems can also scale better for extremely large numbers of targets, but they often add complexity and make it harder to detect failed or silent services.
### Q6 What are the four main components of the Kubernetes control plane, and what is the responsibility of each?
The Kubernetes control plane is responsible for managing the overall state of the cluster and ensuring that the desired state defined by users is maintained. It consists of four main components: the API Server, etcd, Scheduler, and Controller Manager, each with a distinct role in cluster operation.

The API Server is the front door of the control plane, handling all requests from users and internal components and validating and updating cluster state. etcd is a distributed key-value store that persistently stores all cluster configuration and state data. The Scheduler watches for newly created Pods without assigned nodes and decides where to run them based on resource availability and constraints. The Controller Manager runs background control loops that continuously compare the current cluster state with the desired state and take actions (such as creating or restarting Pods) to reconcile any differences.
### Q7 What is kubelet and what role does it play on a Kubernetes worker node?
The kubelet is the primary node agent that runs on every Kubernetes worker node. It is responsible for ensuring that containers described in Pod specifications are running and healthy on that node.

The kubelet communicates with the API Server to receive Pod specifications and continuously monitors the state of the containers. It works closely with the container runtime (such as containerd) to start, stop, and manage containers. Additionally, the kubelet performs health checks, reports node and Pod status back to the control plane, and ensures that the actual state of the node matches the desired state defined in Kubernetes.
### Q8 What is etcd in Kubernetes, and why is it critical to the cluster's operation?
etcd is a distributed, consistent key-value store used by Kubernetes to persist all cluster data. It stores the entire state of the cluster, including information about Pods, Services, Deployments, ConfigMaps, Secrets, Nodes, and other configuration objects.

etcd is critical because it acts as the single source of truth for the cluster. Every change made through the Kubernetes API (such as creating or deleting a Pod) is recorded in etcd. The control plane components continuously read from and write to etcd to maintain and reconcile the desired state of the system.

If etcd becomes unavailable or corrupted, the Kubernetes cluster cannot function properly, because the control plane would lose access to its state data. For this reason, etcd must be highly available, regularly backed up, and carefully protected to ensure cluster reliability and consistency.
### Q9 What is kube-proxy and how does it enable Service networking in Kubernetes?
kube-proxy is a network component that runs on each Kubernetes worker node. Its main responsibility is to implement Kubernetes Service networking by managing network rules that allow traffic to reach the correct backend Pods.

When a Service is created, Kubernetes assigns it a virtual IP (ClusterIP). kube-proxy watches the API Server for changes to Services and Endpoints, and then configures the node’s networking rules (typically using iptables or IPVS) to forward traffic from the Service’s virtual IP to one of the matching Pods. This enables load balancing across multiple Pods that back the same Service.
### Q10 How does the Kubernetes Scheduler decide which node to place a Pod on? What factors does it consider?
The Kubernetes Scheduler is responsible for assigning Pods to suitable worker nodes. When a Pod is created without a node assignment, the scheduler watches for it and selects the most appropriate node through a two-step process: filtering and scoring.

First, during the filtering (predicates) phase, the scheduler eliminates nodes that do not meet the Pod’s requirements. It checks factors such as CPU and memory availability, node taints and tolerations, node selectors, affinity and anti-affinity rules, and whether required volumes can be mounted. Only nodes that satisfy all hard constraints remain as candidates.

Next, during the scoring (priorities) phase, the scheduler ranks the remaining nodes based on preference rules. It considers resource balance, spreading Pods across nodes to improve availability, topology constraints (such as zones or regions), and other scoring plugins. The node with the highest score is selected, and the Pod is bound to that node.
